# data/snapshots — 일일 스냅샷 파일의 성격

이 폴더는 CLNS 가 매일 04:00(KST) 적재하는 **규제 상태 지문**을 JSON 한 장씩 보관합니다.
서버는 기동할 때 이 파일들을 DB 로 복원해(`python -m import_compliance.snapshots --seed`)
무료 플랜 재배포 뒤에도 시계열이 사라지지 않게 합니다.

파일마다 `origin` 필드가 그 날짜가 **어떻게 만들어졌는지**를 밝힙니다. 같은 폴더에 두 종류가
섞여 있으므로, 읽을 때 이 표를 먼저 보세요.

| 파일 | `origin` | 내용 | 시드 복원 | 전일 대비 계산 |
| --- | --- | --- | --- | --- |
| `2026-10-23.json` ~ `2026-11-19.json` (28장) | `backfilled` | **건수 요약만**(`items` 없음). 과거 이벤트 날짜(리콜 등록일·처분 확정일)로 그날의 누적 상태를 **되살린 재구성값** | ❌ (항목이 없어 복원 불가) | ❌ (쓰지 않음) |
| `2026-11-20.json` 이후 | `observed` | 그날 04:00 에 실제로 수집한 상태 + 비교용 `items` | ✅ | ✅ |

## 오해하지 말 것

- 2026-10-23~11-19 의 28장은 **실제로 그날 관측한 값이 아닙니다.** 모두 마지막 수집 시점의
  누적 건수(리콜 846 · 행정처분 0 · 금지성분 11·10 · 성분 사전 548, 합계 1,415)를 이벤트
  날짜 기준으로 다시 계산해 넣은 것이라 **날짜마다 숫자가 같습니다.** 이 숫자를 "그날의
  신규 리콜"로 읽으면 안 됩니다.
- 이 28장은 `items` 가 없어 `seed_snapshots` 가 **`counts_only`** 로 분류하고 건너뜁니다.
  손상된 파일(`unreadable`)과는 다릅니다 — `/v1/meta` 의 `persistence` 블록에서
  `counts_only_days` 로 확인할 수 있습니다.
- 실관측 시계열은 `2026-11-20` 부터입니다. `/v1/trends` 의 `series[].origin` 이 날짜별로
  `observed`/`backfilled` 를 구분해 알려 주고, `coverage.observed_days` 가 실관측 일수입니다.
- 이 폴더의 파일은 90일 보관입니다(`.github/workflows/daily-snapshot.yml` 의 정리 단계).

## 왜 지우지 않고 두나

`origin` 표시와 위 설명만으로 충분히 구분되고, 28장은 날짜별 건수 비교라는 참고 가치가
있습니다. 실관측 파일(`2026-11-20` 이후)은 **절대 지우거나 합치지 마세요** — 무료 플랜
재배포 때 시계열을 되살리는 유일한 원본입니다.
